# Prose review

ใช้ตรวจข้อความใน Step 00–06, workbook Markdown และ review gate message ระหว่าง [self-review](../SKILL.md#self-review-ก่อน-review-gate). เกณฑ์คือผู้ทบทวนอ่านรอบเดียวแล้วตัดสินใจได้.

[Writing style guidance](../../principle-reviewer-first/references/writing-style.md) เป็นเจ้าของรายการ contract tokens และ patterns พื้นฐาน. ไฟล์นี้เพิ่มข้อตรวจที่รายการนั้นไม่มี. ถ้าขัดกัน ให้ contract tokens ชนะ.

ดัดแปลงจาก skill `technical-writing` และ `unslop` ของ pstack สำหรับ planning artifacts ภาษาไทย.

## ลำดับการตรวจ

1. อ่านส่วนเหนือ `ภาคผนวก` และคอลัมน์คำอธิบายในตาราง เช่น Notes, Rationale, Impact และ Mitigation.
2. ตรวจตาม 3 ตารางด้านล่าง แล้วแก้ที่ artifact เจ้าของ.
3. ถามตัวเองว่า "ประโยคไหนยังอ่านแล้วรู้ว่า AI เขียน" แล้วแก้ที่เหลือ.

แก้เฉพาะประโยคที่ติดเกณฑ์. ไม่เรียบเรียงประโยคที่ไม่มีปัญหา เพราะ diff ที่ไม่จำเป็นทำให้ผู้ทบทวนต้องอ่านซ้ำ.

## ประโยคอ่านได้ความหมายเดียว

| ตรวจ | ตัวอย่างที่ต้องแก้ | เขียนเป็น |
|---|---|---|
| หนึ่งประโยคมีหนึ่งความคิด | "Integration กับระบบ HR ยังไม่มี spec ซึ่งทำให้ QA เริ่มไม่ได้และต้องเพิ่ม contingency รวมถึงถามลูกค้า" | แยกเป็นข้อเท็จจริง, ผลกระทบ และ action อย่างละประโยค |
| ระบุผู้กระทำ | "ต้องมีการยืนยัน API spec ก่อนสัปดาห์ที่ 4" | "ทีม IT ของลูกค้ายืนยัน API spec ก่อนสัปดาห์ที่ 4" |
| เงื่อนไขอยู่ก่อนคำสั่งหรือผล | "เพิ่ม 12 MD ถ้าลูกค้าเลือก on-premise" | "ถ้าลูกค้าเลือก on-premise ให้เพิ่ม 12 MD" |
| กรณีหลักอยู่ก่อนข้อยกเว้น | เปิดย่อหน้าด้วยข้อยกเว้นของ scenario | บอก baseline ก่อน แล้วตามด้วยข้อยกเว้น |
| คำจำกัดอยู่ติดคำที่จำกัด | "รวมเฉพาะ SG1 ใน Raw MD ของ mobile" เมื่อหมายถึง mobile เท่านั้น | "Raw MD ของ mobile รวม SG1 เท่านั้น" |
| สรรพนามชี้สิ่งเดียว | "ระบบส่งข้อมูลให้ gateway แล้วมันตอบกลับช้า" | เขียนชื่อซ้ำ: "gateway ตอบกลับช้า" |
| หนึ่งชื่อต่อหนึ่งสิ่ง | "ระบบติดตามรถ", "แพลตฟอร์ม GPS" และ "tracking service" สำหรับสิ่งเดียวกัน | เลือกชื่อเดียวตาม artifact เจ้าของ แล้วใช้ทุกที่ |
| ไม่ใช้ `/` แทนคำเชื่อม | "web/mobile", "และ/หรือ" | "web และ mobile" หรือ "web, mobile หรือทั้งสอง" |
| เขียนประโยคเต็ม | "Spec ล่าช้า → QA เลื่อน, +5 MD" | "ถ้า spec ล่าช้า QA เลื่อนตาม และ effort เพิ่ม 5 MD" |

ประโยคยาวที่มีความคิดเดียวพร้อมเงื่อนไขให้คงไว้ได้. ตาราง, formula และ canonical numeric block ใช้รูปแบบตาม contract และไม่อยู่ใต้กฎประโยคเต็ม.

## ข้อความมีเนื้อหาเฉพาะของโครงการ

| ตรวจ | ตัวอย่างที่ต้องแก้ | เขียนเป็น |
|---|---|---|
| ประโยคที่ย้ายไปเอกสารโครงการอื่นได้โดยไม่ต้องแก้ | "Integration มีความซับซ้อนและอาจกระทบ timeline" | ระบุ integration, สาเหตุ, จำนวน MD หรือสัปดาห์ และ ID. ถ้าระบุไม่ได้ให้ตัดทิ้ง |
| คำขยายแทนตัวเลข | "เพิ่ม effort อย่างมีนัยสำคัญ", "ลดลงมาก" | ใส่ค่าและหน่วยจาก canonical numeric block หรืออ้าง block นั้น |
| แหล่งอ้างอิงลอย | "ตาม best practice", "โดยทั่วไปโครงการลักษณะนี้" | อ้าง source, `REQ-`, `ASM-` หรือ calibration reference. ถ้าไม่มีให้ติดป้าย `Assumption:` |
| คำเปรียบเปรยและศัพท์ที่คิดขึ้นเอง | "รากฐาน", "เสาหลัก", "จุดคานงัด", "north star" | คำตรงตัว หรือชื่อ component, role หรือ step จริง |
| บทสรุปทั่วไป | "แผนนี้ช่วยให้โครงการเดินหน้าได้อย่างมั่นใจ" | จบที่ข้อเท็จจริง, decision หรือ action สุดท้าย |
| คำยาวที่มีคำสั้นกว่า | "ดำเนินการจัดทำ", "ในกรณีที่", "เพื่อที่จะ", "utilize" | "ทำ", "ถ้า", "เพื่อ", "use" |
| คำหรู แทน "เป็น" หรือ "มี" | "ทำหน้าที่เป็น", "ถือเป็น", "serves as" | "เป็น" หรือ "มี" |

## รูปแบบไม่บังคับเนื้อหา

| ตรวจ | ตัวอย่างที่ต้องแก้ | เขียนเป็น |
|---|---|---|
| รายการ 3 ข้อที่เติมให้ครบ | ความเสี่ยง 3 ข้อ โดยข้อ 3 ซ้ำความหมายข้อ 1 | ใช้จำนวนที่มีจริง |
| ช่วงที่ไม่ได้อยู่บนสเกลเดียวกัน | "ตั้งแต่ UI จนถึง governance" | ระบุรายการตรง ๆ |
| Bullet ที่ label ซ้ำเนื้อความ | "**Performance:** Performance ของระบบ..." | เขียนเป็นประโยค หรือคง label เฉพาะ field ของ contract |
| Bullet ที่ไม่ขนานกัน | ข้อ 1 เป็นคำนาม ข้อ 2 เป็นประโยคคำสั่ง | ใช้โครงสร้างเดียวกันทั้งรายการ |
| Heading ที่บอกแค่หัวข้อ | Heading ที่เพิ่มเองนอก contract เช่น "ข้อสังเกต" | บอกประเด็น เช่น "API spec ของ gateway ยังไม่ยืนยัน". Heading ของ contract คงตามเดิม |

## สิ่งที่ prose review ห้ามทำ

- ห้ามแก้ contract tokens: headings, IDs, ตัวเลข, formulas, field labels, status words และ defined terms.
- ห้ามเพิ่มหรือลบ fact, source, owner หรือ date. รายละเอียดที่ขาดให้บันทึกเป็น Open item.
- ห้ามเปลี่ยนระดับข้อผูกพัน เช่น "ต้อง", "ควร" และ "อาจ" และห้ามเปลี่ยน evidence status เช่น `Assumption` เป็น `Confirmed`.
- ห้ามแก้ข้อความที่คัดจาก TOR หรือคำพูดของผู้ใช้.
